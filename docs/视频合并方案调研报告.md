## 一、调研范围与项目筛选说明

### 1.1 筛选口径

视频"拼接"这个词在工程上覆盖了三种完全不同的实现层次，混在一起比较会得出错误结论。因此本次按**实现层次**分层取样，每一层都选该层最具代表性、源码可读的项目：

| 层次 | 本质 | 代表 |
|---|---|---|
| **A. 容器层直拼**（sample table 重写） | 不解码，直接搬 sample，重写时间戳表 | mp4parser、GPAC/MP4Box |
| **B. 封装层流复制**（concat demuxer + `-c copy`） | 让 ffmpeg 把多文件的包当作"已混流"顺序读出 | LosslessCut、vidmerger、clip-join、Opencast |
| **C. 帧级合成 / 滤镜重编码** | 解码到帧，重新合成、重新编码 | moviepy、editly、ffmpeg-concat、MLT |

### 1.3 排除项与理由

- 纯 GUI 套壳、无源码或压缩混淆分发的商业工具（如各类"视频合并大师"）。
- 仅做"同一文件内多片段裁剪后合并"的工具（形态更接近剪辑器，不与跨文件合并同类）。
- 依赖私有云服务的在线合并站点。
- 只提供 API、无可读实现的 SaaS SDK。

## 二、代表性项目对比

### 2.1 总览

| 项目 | 实现路径 | 何时不重编码 | 无损判据（比对哪些参数） | 参数不一致时的回退 |
|---|---|---|---|---|
| **LosslessCut** | concat demuxer + `-c copy`，清单经 **stdin** 灌入 | 全一致时 | codec_name / width / height / pix_fmt / level / profile / sample_fmt / r_frame_rate / time_base（**故意不比 avg_frame_rate**） | 报错 + 引导性对话框（换输出格式、关掉 merge options、换工作目录） |
| **mp4parser** | 重写 stbl（stts/ctts/stss/stsc/stsz/stco） | 全一致时 | stsd 逐字段 + esds 深度比对（AudioSpecificInfo、objectTypeIndication 等） | **抛 IOException**，无转码能力 |
| **GPAC / MP4Box** | 逐 sample 复制 + 改写 DTS/CTS + 合并 SPS/PPS | 全一致或参数集可合并时 | sample description / subtype / 宽高 / AVC profile-level / HEVC profile-level-compat / SPS-PPS | 合并 config → 新建轨道 → `-force-cat` 强拼（**从不转码**） |
| **vidmerger** | concat demuxer + `-c copy`，前置 fps 对齐 | 全一致时 | 音频 codec + sample_rate + channels、流布局（kind+codec 有序）、尺寸众数、额外流 | 任一不合 → **全部**转换；`unsupported type` → 再全转一次 |
| **clip-join** | concat demuxer + `-c copy`，失败降级重编码 | codec + 分辨率一致 + 白名单 | 只有 **codec_name + 宽×高**（+ HEVC 平台白名单） | 失败后**全量** libx264 CRF18 / AAC 192k |
| **moviepy** | 帧级 Python 合成 | 从不 | 无（不探测、不比对） | 无回退概念，始终重编码 |
| **editly** | 声明式时间轴 → ffmpeg 全量重编码 | 从不 | 无 | 统一 width/height/fps 后重编码 |
| **ffmpeg-concat** | OpenGL 渲染转场帧 → 重编码 | 从不 | 无 | 以首段尺寸/fps 为基准 |
| **MLT** | producer / playlist / tractor 模型 | 取决于 profile 与消费者 | 由 profile 决定 | 交给消费者（melt 编码） |

### 2.2 LosslessCut —— 工程细节最完整的一套

**拼接核心**（`src/renderer/src/hooks/useFfmpegOperations.ts`）：清单**不落盘**，直接经 stdin 喂给 ffmpeg：

```ts
addInput(['-f', 'concat', '-safe', '0', '-protocol_whitelist', 'file,pipe,fd', '-i', '-']);
...
const concatTxt = paths.map((file) => `file 'file:${resolve(file).replaceAll('\'', String.raw`'\''`)}'`).join('\n');
```

主进程侧 `runFfmpegConcat` 只负责 spawn 与进度：

```ts
const process = runFfmpegProcess(ffmpegArgs);
handleProgress(process, totalDuration, onProgress);
stringToStream(concatTxt).pipe(process.stdin);
```

**兼容性判据**（`src/renderer/src/components/ConcatDialog.tsx`）——这份字段清单是本次调研中**最克制也最有依据**的：

```ts
// check all these parameters
// avg_frame_rate is not checked, because it often differs slightly between files that merge fine https://github.com/mifi/lossless-cut/issues/2759
(['codec_name', 'width', 'height', 'pix_fmt', 'level', 'profile', 'sample_fmt', 'r_frame_rate', 'time_base'] as const).forEach((key) => {
```

配套 UI 把差异做成表格（Track / Parameter / Expected / Actual），失败时有专门的引导对话框（换成 MOV、换输出格式、关掉 merge options、换工作目录）。

**优点**：判据与"真实失败原因"对齐；`-safe 0` + `-protocol_whitelist` 解决了绝对路径与 pipe 的两个经典坑；进度解析、全局 abort（`runningFfmpegs` + `AbortController`）都做成了基础设施；`transferTimestamps` 保留源文件时间戳。
**不足**：只判定"能不能 copy"，一旦确定要重编码就整段重来，没有"只修不匹配段"；用户被要求在多个对话框之间试错，而不是自动降级。

### 2.3 mp4parser —— 容器层最严谨，但也最不宽容

`AppendTrack` 把各段 sample 列表直接首尾相接，**DTS 不做加法偏移**，而是把各段 `getSampleDurations()` 拼成一个 `long[]` 交给 builder 折叠成 stts：

```java
for (Track track : tracks) { lists.addAll(track.getSamples()); }
decodingTimes = new long[numSamples];
```

ctts 用 `blowupCompositionTimes()` 展开成逐 sample 偏移后重建，**跨段不平移**——因此隐含要求每段起点必须是随机访问点（IDR）。stss 的同步样本序号会加上 `samplesBefore` 重定位。

参数比对在 `mergeVisualSampleEntry` / `mergeAudioSampleEntries`：宽高、depth、frameCount、`Arrays.equals` 子 box、以及 `esds` 里 `ESDescriptor` / `AudioSpecificInfo` 的深度比对；只有 bitrate 这类字段被宽容处理（求平均 / 取 max）。任一不等即 `return null` → 上层抛 `IOException`。

README 原文：

> "It is important to emphasize that you cannot append any two tracks with: Different resolutions, Different frame-rates"

**优点**：真·零解码，速度只受磁盘限制；跨段 timescale 有 `ChangeTimeScaleTrack` 兜底；`ClippedTrack` 的 docstring 明确把"fromSample 必须是 random access sample"的责任写清（见 [ClippedTrack.java](https://github.com/sannies/mp4parser)）。
**不足**：判据过严（profile/level 差一点、SPS/PPS 不同就失败），手机素材实测失败率高；**没有转码能力，失败即终止**；文档薄，1.x→2.x 的 `CroppedTrack`→`ClippedTrack` 改名无迁移说明。

### 2.4 GPAC / MP4Box —— 唯一尝试"智能合并"而不是"直接放弃"的实现

选项语义（`applications/mp4box/mp4box.c`）：

```c
MP4BOX_ARG("cat", "concatenate given file samples to file, creating tracks if needed. ... Note: This aligns initial timestamp of the file to be concatenated", ...)
MP4BOX_ARG("unalign-cat", "do not attempt to align timestamps of samples in-between tracks", ...)
MP4BOX_ARG("force-cat", "skip media configuration check when concatenating file. Warning: THIS MAY BREAK THE CONCATENATED TRACK(S)", ...)
```

三个值得抄的细节：

1. **对齐基准用最后一个 sample 的 DTS + duration，而不是 duration**：
   ```c
   //get next sample DTS - we do NOT use media duration as CTS offset could shift up everything
   u64 track_dur = gf_isom_get_sample_dts(dest, i+1, last_samp);
   track_dur += gf_isom_get_sample_duration(dest, i+1, last_samp);
   ```
   因为 `mdhd` 的 duration 与真实末帧 DTS 可能不等（B 帧 CTS 偏移会把内容推出 duration 之外）。
2. **不匹配时先尝试"合并"再放弃**：NAL 长度字段不同则 `gf_media_nal_rewrite_samples` 重写，SPS/PPS 尝试并入，实在不行转 in-band 参数集，再不行 `gf_isom_clone_track` 新建轨道。
3. `-force-cat` 的真实作用点只是把"放弃"改成"带警告硬拼"，并打印 `WARNING: Concatenating track ID %d even though sample descriptions do not match`。

**优点**：不匹配场景下的处理纵深是这批项目里最强的；`-catpl` 支持播放列表批量。
**不足**：**完全没有重编码路径**，分辨率/编码不同只能报错或产出多轨道；`-unalign-cat` 的 `2*dts[n]-dts[n-1]` 外推在变帧率素材上会出毛刺；wiki 的 concatenation 专页已下线，语义只能从自动生成文档 + 源码反推。

### 2.5 vidmerger —— 判据最贴近 `-c copy` 的真实约束

ffprobe 探测字段：

```rust
"-show_entries", "stream=codec_type,codec_name,sample_rate,channels:stream_disposition=attached_pic"
```

决策逻辑里有一句注释，直接解释了为什么"只重编码一段"在实践中几乎不存在：

```rust
// Converted inputs always get H.264 video, so copied inputs could have a different video
// codec and break `-c copy`. If any input is converted, convert all of them.
let convert_all = force_convert || decisions.iter().any(|(convert, _)| *convert);
```

fps 对齐是**独立的预处理阶段**：`fps_goal = fps_from_cli != 0 ? fps_from_cli : min(all fps)`，只对不等的文件跑 `-r` 到临时目录后重写清单。回退还有一层：`stderr.contains("unsupported type")` 时全量转码重试（对应 .mov 里的 `tmcd` 流）。

**优点**：覆盖"流数量/顺序/额外流"，这是 LosslessCut 与 clip-join 都没覆盖的；先用 min fps 对齐再 copy，正面解决最常见的音画漂移；章节元数据一并写入。
**不足**：**不比较 time_base、pix_fmt、H.264 profile/level**——同 codec 不同 profile 仍可能被播放器拒绝；任一不合即全量转码，代价大。

### 2.6 clip-join —— 降级体验最好，判据最粗

```ts
// Codecs safe to stream-copy straight into an .mp4. H.264 plays everywhere.
// HEVC ... is NOT safe on stock Windows ... "Missing codec", 0xc00d5212
const SAFE_COPY_CODECS = new Set(["h264"]);
export function canLossless(clips: Clip[]): boolean {
  const first = included[0].videoSignature;              // `${codec_name} ${width}x${height}`
  if (!included.every((c) => c.videoSignature === first)) return false;
  if (codec === "hevc" || codec === "h265") return process.platform !== "win32";
  return SAFE_COPY_CODECS.has(codec);
}
```

降级路径：

```ts
if (!forceReencode && canLossless(included)) { /* -c copy 先试，code===0 即返回 */ }
/* 否则 libx264 -crf 18 -preset veryfast + aac 192k */
```

值得注意的是它**转场分支反而做了完整归一化**，恰好补齐了 `canLossless` 缺失的检查项：

```ts
`[${i}:v]fps=${fps},scale=${w}:${h}:force_original_aspect_ratio=decrease,` +
`pad=${w}:${h}:(ow-iw)/2:(oh-ih)/2,setsar=1,format=yuv420p,settb=AVTB[v${i}]`
```

工程细节：Windows 反斜杠→正斜杠归一化、单引号转义、`-progress pipe:1` 解析 `out_time_us`、`windowsHide: true` 防控制台闪窗、探测并发池。

**优点**：`canLossless` 短到能一眼看穿，UI 明示 lossless / reencode；"先 copy 失败再重编码"的降级链完整可用。
**不足**：**只比 codec + 分辨率两项**——同 h264 同分辨率但 30fps vs 25fps、音频 44.1k vs 48k、有无音轨都没有拦住，只能靠 ffmpeg 退出码兜底；而 concat demuxer 的部分失败是**静默的**（exit 0 但音画漂移），此时不会触发回退。

### 2.7 moviepy —— 最灵活，也最昂贵

`concatenate_videoclips(clips, method="chain" | "compose")`（[CompositeVideoClip.py](https://raw.githubusercontent.com/Zulko/moviepy/master/moviepy/video/compositing/CompositeVideoClip.py)）：

```python
if method == "chain":
    def frame_function(t):
        i = max([i for i, e in enumerate(timings) if e <= t])
        return clips[i].get_frame(t - timings[i])
elif method == "compose":
    w = max(size[0] for size in sizes); h = max(size[1] for size in sizes)
    result = CompositeVideoClip([clip.with_start(t).with_position("center") ...], size=(w, h), ...)
fpss = [clip.fps for clip in clips if getattr(clip, "fps", None) is not None]
result.fps = max(fpss) if fpss else None
```

- `chain`：纯索引切片，**不校正尺寸**，直接写文件会拉伸错位（docstring 明确劝阻）。
- `compose`：取**最大宽高**做画布、小的居中、空白填 `bg_color`——是"放大画布"而不是"缩小素材"。
- 帧率：取**最高 fps**，低 fps 段靠浮点时间轴重复取帧，不是真正的帧率转换。
- 音频：各段 `CompositeAudioClip` 按起始时间叠放。

**优点**：任意分辨率/帧率/编码混拼都不会失败；mask、负 padding 重叠、转场插片一应俱全；可编程性最强。
**不足**：**永远全量重编码**（40×1GB 素材要跑几小时，与 clip-join 的"秒级"形成对照）；`chain` 尺寸不一致产出坏画面；`max(fpss)` 在高/低帧率混排时观感不自然。

### 2.8 editly / ffmpeg-concat / MLT / OpenTimelineIO —— 另四种范式

| 项目 | 范式 | 关键点 |
|---|---|---|
| **editly** | 声明式 NLE | 配置层强制统一 `width`/`height`/`fps`（默认 640、首段 fps 或 25），逐 clip 生成 filter graph；`createConcatFile` 复用 `file '...'` + `'''` 转义 |
| **ffmpeg-concat** | 帧级 + OpenGL 转场 | 抽帧 → 用 `gl-transition` 在 GPU 上渲染转场 → 回编码；`init-frames` 里 **"first video dictates dimensions and fps"**，`duration = Σscene.duration - Σtransition.duration` |
| **MLT** | 时间轴引擎 | `producer` + `playlist`（`mlt_playlist_append_io` 支持 in/out 点）+ `tractor`/`multitrack` 合成；不决定编码，交给消费者 profile |
| **OpenTimelineIO** | 交换格式，不是合并器 | Timeline/Track/Clip/Gap/Transition + `Stack` 从底到顶 painter order 合成；价值在于"把合并意图结构化"，实际渲染仍旁路到 ffmpeg |

## 三、共性能力与差异化特色

### 3.1 五个共性能力

1. **参数指纹比对是"能否无损"的唯一入口**。所有 B 类项目都先做 ffprobe，再与首段比对。差异只在校验字段的多少。
2. **清单文件的引号/路径处理是必踩的坑**。`file '...'` 里含单引号要写成 `'\''`；Windows 反斜杠会被当转义（clip-join 直接换成正斜杠）；新版 ffmpeg 要求 `file:` 前缀，否则报 `Impossible to open 'pipe:xyz.mp4'`。
3. **进度必须从 `-progress`/`stats` 流里解析**，而不是等进程退出（clip-join 用 `-progress pipe:1` 解析 `out_time_us`，LosslessCut 解析 stderr 的 `time=`）。
4. **输出格式/容器是独立自由度**，与"能否 copy"正交——LosslessCut 的失败引导里第一条就是"换成 MOV 试试"。
5. **无人能自动修好一切**：A 类选择"报错"，B 类选择"全量重编码"，C 类根本不判断。**没有实现选择"只重编码不匹配的那一段"**——vidmerger 的注释给出了原因：一旦某段被重编码，codec 就不再统一，`-c copy` 的前提被打破。

### 3.2 三个真正的差异化特色

| 特色 | 谁做得最好 | 说明 |
|---|---|---|
| **差异可视化 + 可解释** | LosslessCut | 把 mismatch 做成 Track/Parameter/Expected/Actual 表格，用户知道"到底哪里不一样" |
| **不匹配时的处理纵深** | GPAC | 合并 SPS/PPS → 重写 NAL 长度 → in-band 参数集 → 克隆轨道 → `-force-cat`，五级递进 |
| **判据贴近真实约束** | vidmerger | 唯一同时覆盖"流数量/顺序/额外流/采样率/声道"的，因为它是从真实 issue（`tmcd` 流、`unsupported type`）反推出来的 |

### 3.3 concat demuxer 的静默失败模式（本节是整份报告的技术核心）

FFmpeg 官方的措辞已经把风险说透了：

> "All files must have the same streams (same codecs, same time base, etc.). **The duration of each file is used to adjust the timestamps of the next file: if the duration is incorrect (because it was computed using the bit-rate or because the file is truncated, for example), it can cause artifacts.**"
> —— https://ffmpeg.org/ffmpeg-formats.html#concat-1

Opencast 把后果讲得更直白：

> "A *same codec* mode which assumes the restriction is already met and can hence concatenate the files much faster while also being a lossless process. **But it will fail or produce a weird output if the restrictions are not met.**"

按危害排序的失败模式：

| # | 失败模式 | 表现 | 退出码 | 谁能发现 |
|---|---|---|---|---|
| 1 | **time_base 不一致** | 后续段整体漂移、空洞、音画错位几帧到几百毫秒 | **0（静默）** | 只有参数比对（LosslessCut / vidmerger 部分） |
| 2 | **音频比视频短**（AAC priming/padding 每段 20–40ms） | 同步误差随段数累积，20 段近 1 秒 | 0（静默） | 只有成品时长/音轨 PTS 校验 |
| 3 | **DTS 非单调 / 负起始** | `Non-monotonically increasing dts`、丢帧 | 可能 0 | ffmpeg 日志 |
| 4 | **段首非 IDR/关键帧** | 从第二段起花屏、首帧绿 | 0（静默） | 只有全片解码校验 |
| 5 | **SPS/PPS（extradata）不同** | "能播但花屏/黑屏"，`-c copy` 只留首段 `avcC` | 0（静默） | 只有解码校验 / 播放器 |
| 6 | **流数量/类型不一致** | 报错，或静默丢轨（无音轨段输出无声） | 非 0 或 0 | 参数比对 |
| 7 | **pix_fmt / SAR 不一致** | 某几段被拉伸，或播放器拒绝 | 0 或非 0 | 参数比对 |
| 8 | **路径/引号** | `Unsafe file name`、`Impossible to open` | 非 0 | 显式报错 |

**关键结论：concat demuxer 的"同一 streams"是必要条件而非充分条件。** 真正决定成败的是 duration 是否精确、每段首帧是否 IDR、extradata 是否一致——三者任一不满足都可能以 **exit code 0 产出坏文件**。因此：

> **不能用退出码作为"无损成功"的唯一信号。** 必须补一次成品校验。

这一条恰好是本项目已经踩过的坑：**抽样校验（开头 1 秒 + 结尾 2 秒）根本碰不到段间接缝**。

## 四、可借鉴的功能 / 设计 / 实现方案

### 4.1 与本项目现状的对照

本项目当前的三级策略（见 [MergeCompatibility.cs](src/SubFusion.Core/Merge/MergeCompatibility.cs)）：

| 档位 | 触发条件 | 实现 |
|---|---|---|
| `CanStreamCopy` | 参数全一致 | concat demuxer + `-c copy` |
| `CanRemuxOnly` | 差异**全部**落在 `MergeReasonFix.Remux`（时基、H.264/HEVC 帧率） | 逐段 `-c copy` 重封装统一时基，再 concat |
| `NeedsReencode` | 其余差异 | 逐段统一重编码 |

对照调研结果：

| 能力 | 本项目 | 业界最优 | 判断 |
|---|---|---|---|
| 参数判据覆盖面 | codec/profile/resolution/pixfmt/fps/timebase/SAR/色彩/流数/音频/容器 | LosslessCut 9 项；vidmerger 6 类 | **本项目已超出所有调研对象** |
| 帧率差异分编码处理 | mpeg4 系列必须重编码，H.264/HEVC 可重封装 | 无人区分（clip-join 直接忽略 fps） | **独有，且有实测支撑** |
| 中间档 `RemuxOnly` | 有 | **无人有** | **独有**（LosslessCut 只有二选一） |
| 成品校验 | `OutputVerifier.CheckFullDecodeAsync` 全片解码 | 无人做 | **独有** |
| 按名称自然排序 | `NaturalComparer`（数字段数值比较、忽略前导零） | clip-join 仅 `localeCompare` | 有改进空间但已优于调研对象 |
| 无损组合识别 | `MergeGrouping`（贪心聚类 + 两次 pass） | **无人有** | **独有** |
| 校验后删源 | `DeleteSourceAfterVerify` + 强制耦合 `VerifyOutput` | **无人有** | **独有** |

### 4.2 值得直接抄的五个具体做法

**① 对齐基准用"末 sample 的 DTS + duration"，不要用 duration**（来自 GPAC）
```c
// we do NOT use media duration as CTS offset could shift up everything
u64 track_dur = gf_isom_get_sample_dts(dest, i+1, last_samp);
track_dur += gf_isom_get_sample_duration(dest, i+1, last_samp);
```
本项目重封装路径目前靠 `-video_track_timescale 90000` 统一时基，这是容器层做法，等价效果好；但如果将来需要写 concat 清单的 `duration` 指令（`duration dur` 覆盖文件内的错误时长），应取末帧 DTS+duration 而非 `format.duration`。

**② concat 清单可以走 stdin，不必落盘**（来自 LosslessCut）
`-f concat -safe 0 -protocol_whitelist file,pipe,fd -i -` + 把清单 pipe 进 stdin。省一次磁盘写入，也天然避免临时清单残留。本项目当前落临时文件——在 `tempDir` 已按 taskId 隔离的前提下可以接受，但 stdin 更干净。

**③ 路径归一化 + 引号转义要一次做对**（来自 clip-join / LosslessCut）
- Windows：`p.replace(/\\/g, "/")`（ffmpeg 的 concat 解析器把反斜杠当转义）
- 单引号：`p.replace(/'/g, "'\\''")`
- 新版 ffmpeg 要求 `file:` 前缀

**④ 差异要能"说给人听"**（来自 LosslessCut 的 mismatch 表格）
本项目 `MergeReason(Code, Detail, Fix)` 的结构已经具备这个能力（`Detail` 是中文自然语言），但 UI 上可以再压一层：把多为 `Reencode` / 多为 `Remux` 聚合显示，而不是并列一长串。

**⑤ 失败对话框要给出"下一步该试什么"**（来自 LosslessCut）
LosslessCut 的 `showConcatFailedDialog` 列了 6 条可操作建议（换容器、关 merge options、换工作目录、换文件……）。本项目目前是直接抛 ffmpeg stderr 末几行——可读性上可以按 stderr 关键词映射到建议（`Non-monotonically` → 时基问题建议重封装；`Invalid data` → 编码不一致建议重编码）。

### 4.3 明确**不建议**照搬的做法

| 做法 | 出处 | 为什么不抄 |
|---|---|---|
| 只比 codec + 分辨率就判定可无损 | clip-join | 覆盖不足，会把 30/25fps、44.1k/48k 混拼放过去，然后靠 exit 0 兜底——静默损坏 |
| 任一不合即全量重编码 | clip-join / vidmerger | 本项目已有 `RemuxOnly` 中间档，全量重编码是倒退 |
| 失败即抛异常 | mp4parser | 桌面工具不能把"参数不匹配"当成不可恢复错误 |
| `-force-cat` 硬拼 | GPAC | 官方警告 "THIS MAY BREAK THE CONCATENATED TRACK(S)"，违背"输出必须可播"的底线 |
| `chain` 模式不做尺寸校正 | moviepy | 产出坏画面的最短路径 |
| 取 `max(fps)` 作为输出帧率 | moviepy | 高低帧率混排观感不自然；应统一到单一目标帧率 |

## 五、风险与限制

### 5.1 技术风险

1. **静默损坏不可由退出码捕获**（本报告 §3.3）。任何"copy 成功即认为成功"的设计都有缺陷。
2. **抽样校验必然漏检**。段间接缝在文件中段，头尾抽样永远碰不到。本项目已改为全片解码——代价是 2.24GB 素材约需数分钟，且**校验时间与素材时长线性相关**，长素材会显著拖慢"删源"路径。
3. **帧率差异的编码依赖性是真约束，不是启发式**。mpeg4 把帧率写进 VOL 头，改容器时间戳无效（`-r` 单独用也没用）；H.264/HEVC 的帧率在 SPS/VPS 里且段间可共存。这条规则一旦被"简化"成统一重编码或统一重封装，都会立刻产生回归。
4. **`-video_track_timescale` 不是万能的**。它统一的是容器时基，不修正段内 VFR 或 duration 与末帧 DTS 的偏差。
5. **全量重编码的"质量-速度"取舍**：本项目对 legacy codec 用 `-q:v`（映射自 Crf-18）、H.264 用 `libx264`/`libx265`。对 `mpeg4` 这类老编码，`q:v` 的量化步长语义与 CRF 不完全等价，跨版本 ffmpeg 行为可能漂移。

### 5.2 调研本身的限制

- **star 数与最近提交时间不能代表质量**：clip-join 仅 11 星但降级链设计清晰；mp4parser 2.8k 星但两年未更新。
- **未能取得一手来源的部分**（已在引用处标注）：
  - mp4parser 的 `AppendTrack.java` / `ClippedTrack.java` 原始文件在本次抓取时被 GitHub 限流/404，节选内容取自可访问的镜像与 fork 转述，**字段清单以 javadoc 与 README 为准**。
  - GPAC 的 concatenation 专页（`wiki.gpac.io/Howtos/Concatenation/`）已 **404**，`sitemap.xml` 中亦无对应条目；选项语义取自 `mp4box.c` 源码与自动生成的 import-opts 文档。
  - vidmerger 的 `LICENSE` 字段 GitHub API 返回空，**许可未确认**。
- **未覆盖方向**：硬件加速（NVENC/QSV/VideoToolbox）在合并场景下的收益；分布式/并行分片合并；HLS/DASH 分片级合并（与"文件级合并"是不同问题）。

### 5.3 本项目特有风险（继承自已验证的结论）

- **删源是不可逆操作**。当前设计（全片解码校验通过才删、默认关闭、关掉校验即强制关掉删源）是正确的，但校验超时也会保留源文件——这会让"校验 30 分钟未完成"变成"源文件没删"，用户可能误以为功能失效。
- **`MergeGrouping` 必须复用 `CompatibilityAnalyzer`**，不能自带一套规则；否则 UI 说"可无损"而引擎说"要重编码"，是最坏的用户体验。
- **贪心聚类而非严格指纹分桶**：严格指纹会把本可合并的文件拆开，但贪心也需要收敛性保护（当前两次 pass）。

## 六、后续改进建议

按"收益 / 成本"排序。

### P0 — 补上"成品校验"的短板（成本低，收益高）

1. **时长一致性断言**：`|输出时长 − Σ输入时长| < 0.5s`（或按帧数容忍 `±2 帧`）。调研中 vidmerger 与 Opencast 都点到 duration 是静默损坏的根因，而本项目目前只校验"能解码"，没有校验"时长对"。**这条能在全片解码之前就用极低成本拦掉大部分漂移类损坏。**
2. **音频 PTS 单调性检查**：`ffprobe -show_packets -select_streams a` 检查 `pts` 是否单调递增。AAC priming/padding 导致的累积漂移正是这一类。
3. **段间接缝定点校验**：在 `Σ前 i 段时长 ± 0.5s` 处各解码 1 秒。相比全片解码，能把 2.24GB 的校验从"数分钟"降到"数秒"，同时**仍能命中接缝**——这是对现有 `CheckFullDecodeAsync` 的重要补充（而非替代）。

> 建议的校验阶梯：**时长断言（毫秒级）→ 接缝定点解码（秒级）→ 全片解码（分钟级）**，逐级升级，只有前一级通过才进入下一级。删源动作仍然要求最后一级通过。

### P1 — 提升"可解释性"

4. **差异聚合展示**：把 `MergeReason` 按 `Fix` 分组（"可重封装解决：时间基准" / "必须重编码：像素格式、分辨率"），而不是平铺。
5. **stderr 关键词 → 可操作建议映射**：`Non-monotonically increasing dts` → "时基不一致，建议允许重封装"；`Invalid data found` → "编码不一致，需要重新编码"；`Unsafe file name` → "路径含特殊字符"。
6. **把 `MergeGrouping` 的判定依据显示到卡片上**：当前有 `KindText`（"直接拼接"/"重封装后拼接"），可以再补一行"为什么不能直接拼"。

### P2 — 对齐业界最佳实践

7. **concat 清单走 stdin**：`-protocol_whitelist file,pipe,fd -i -`，省一次磁盘写入并避免临时清单残留。
8. **路径归一化统一到一个 helper**：`NormalizeConcatPath`（反斜杠→正斜杠 + 单引号转义 + `file:` 前缀），一次性解决 Windows 上所有清单相关的"假故障"。
9. **校验用的 `-loglevel` 分级**：当前全片解码用 `-loglevel error`，可以额外抓 `warning` 级别的 `[concat] DTS out of order` 之类，作为"低置信度但仍应提示"的信号。

### P3 — 需要产品决策

10. **`-c copy` 失败后的自动降级**：目前 `CanStreamCopy` 判定为真就直接 copy，若 ffmpeg 非 0 退出，是否自动改走 `RemuxOnly` → `Reencode` 重试？调研中 clip-join 的做法（先 copy 失败再重编码）体验最好，但会显著拉长失败路径耗时，且与"用户已被告知策略"存在冲突。建议做成**可选开关**而非默认行为。
11. **"只重编码不匹配段"的重新评估**：调研中 5 个开源实现全部放弃这条路径（vidmerger 的注释给出了理由）。本项目当前是"全部重编码"，但如果只有 1 段 mpeg4 帧率不同而其余 9 段一致，全量重编码的浪费是明显的。可行方案是**两阶段**：先把不一致段重编码到统一参数，再对"重编码段 + 原始段"做一次参数复核——若复核通过则走 copy 拼接。这需要 `CompatibilityAnalyzer` 能对"重编码后的预期参数"做预演，属于中等规模改动。

### 12. 建议的下一步动作（不含代码）

- 先做 P0-1（时长断言），它是 **成本最低、覆盖最广**的一条；
- P0-3（接缝定点校验）需要在自检套件里补一组"人为制造中段 seam 损坏"的用例，否则无法证明它真的能命中；
- P1 与 P2 可以合并成一次"可解释性 + 路径健壮性"迭代；
- P3-10 / P3-11 需要产品决策，建议单独出方案再评估。
